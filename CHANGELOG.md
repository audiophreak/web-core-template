## 0.7.0

Optional **native-client** support. Additive: with `native_client` off (the default) every configuration is
byte-identical to 0.6.1 apart from `.copier-answers.yml` (which gains `native_client: false`). No dependency is
added and no lockfile changes.

- New optional feature **`native_client`** (default off; requires `auth`; never enables it for you):
  - Better Auth's **bearer plugin** (`requireSignature: true`): native clients send the signed session token from
    sign-in's `set-auth-token` header as `Authorization: Bearer`. One session table, one expiry, one revocation
    for cookies and bearer tokens; unsigned, forged and malformed tokens are `401 unauthenticated`; origin and
    CSRF checks and the rate limits are unchanged. A password change that revokes other sessions rotates the
    current token (documented).
  - A deterministic **OpenAPI 3.1** contract of `/api/v1` in `openapi/openapi.json`, generated from the Zod
    schemas and verified by `npm run check` (drift, route coverage, security requirements, problem statuses, bounds);
    `npm run openapi:generate` regenerates it. Better Auth's own endpoints stay outside the contract.
  - `docs/native-client.md`.
  - `.prettierignore` and `eslint.config.mjs` leave a native iOS layer's `ios/` (and `.copier-answers.ios.yml`) alone, and `AGENTS.md` tells agents
    to read `ios/AGENTS.md`: the web tooling must not format or lint another template's files. (The only other changed files with
    the feature on are `auth.ts`, `package.json` and `AGENTS.md`.)
  - Response schemas allow unknown fields, and a response string enum (the problem `code`) is an open string whose known
    values are `examples`: a generated client must not fail on a value added within v1. Requests stay strict.
- Tests: `tests/test_native_client*.py`, two end-to-end apps; the feature matrix grows from 16 to 20 selections, the
  lock matrix stays at 11.

## 0.6.1

changes: with `auth` off, every selection is byte-identical to 0.6.0; with `auth` on, only `package.json`

## 0.6.0

Optional authentication feature. Additive: with `auth` off (the default), the output of every selection of
`zod`, `forms`, `rest_api`, `database` and `cache_components` is byte-identical to 0.5.1 apart from
`.copier-answers.yml` (which gains `auth: false`) and, with the `supabase` provider only, two lines in
`.gitignore` (see the fix below). Projects generated by 0.1.x to 0.5.x upgrade cleanly and
keep their selections. Existing lockfiles are unchanged; four are added (eleven in all).

- New optional feature **`auth`** (default off; requires `zod`, `rest_api` and a `database`, any provider;
  independent of `forms`; never enables a prerequisite): email/password authentication with **Better Auth
  1.7.15 for both database providers**, not Supabase Auth (which stays disabled). Better Auth mounts at
  `/api/auth`; sessions live in PostgreSQL, are read on every request and end at once on sign-out, revocation,
  expiry or a password change. Cookies are HttpOnly, SameSite=Lax and Secure (with the `__Secure-` prefix) on
  https; CSRF and origin checks stay on and trusted origins are explicit and narrow; rate limits are Better
  Auth's own, stored in the database, and no client-supplied header is trusted for the client address unless the
  deployment names its own. Open sign-up is off by default in production. There is no committed default secret.
- **Least-privilege runtime role.** The application connects as `app_runtime`, never as the owner: no
  superuser, no CREATEROLE/CREATEDB, no BYPASSRLS, owns nothing, column-level `INSERT`/`UPDATE`. The administrative
  `DATABASE_URL` is for migrations, tests and tools; the application reads `DATABASE_RUNTIME_URL` and refuses to
  do database work if its role is an administrator. `npm run db:init` generates the runtime password and the
  authentication secret (appending only the missing lines to an existing `.env.local`, mode 0600) and
  `npm run db:migrate` applies the password to the role.
- **Owner-scoped data.** `app.items` gains an owner and row level security: the policies read a user id that
  `withPrincipal` sets for one transaction, so a statement that forgot its filter, or a raw query, still sees only
  the caller's rows, with no user it sees none, and a pooled connection cannot carry an identity between
  requests. Another user's item is 404, not 403. New migrations continue the one canonical history
  (`..._create_auth.sql`, `..._scope_items_to_owner.sql`) and nothing changes the schema at runtime; a database
  test asks Better Auth's own schema tooling what it would still have to create and requires the answer to be
  nothing.
- **Protected API v1** (additive; the existing contracts are unchanged): `/api/v1/items` (create, list, read,
  update, delete), `/api/v1/session` and `/api/v1/sessions`, with explicit response schemas, a stable 401
  `unauthenticated` problem and a 403 `origin_not_allowed` for state-changing requests from an untrusted origin.
  The public examples stay public.
- **Dependencies.** One: `better-auth` 1.7.15 (MIT, the newest stable release that was two weeks old),
  adding 20 MIT packages to the `database` lock and no install script. Better Auth declares optional peers
  on frameworks, ORMs and test runners; so that npm does not link the project's own development tools
  (vitest) to them and report their advisories in `npm audit --omit=dev`, the generated project carries an
  `.npmrc` with `legacy-peer-deps=true`, and the locks are produced under the same setting.
- Not included, and documented as the deployer's responsibility in `docs/auth.md`: email verification and
  password-reset delivery (no mail service), open public registration, trusted-proxy and origin configuration,
  secret management and account recovery. Changing the database provider, or disabling authentication, is
  not an upgrade.
- **Fix, for the `supabase` provider with or without `auth`:** the Supabase CLI creates `supabase/.temp` and
  `supabase/.branches` the first time the local stack starts, and the generated `.gitignore` did not ignore
  them, so `copier update` and `devkit upgrade` (which need a clean working tree) refused a project that had run
  its stack. The generated `.gitignore` now ignores both. An existing Supabase project adds the two lines (or
  commits the folders) before its first upgrade; the update itself then brings the lines in.
- New locks: `auth+database-postgres+zod`, `auth+database-supabase+zod` and each with `forms`. New tests:
  Docker-free render, composition and upgrade tests (the old side of the upgrades is the real published
  v0.5.1), and Docker tests that run the whole feature against real PostgreSQL and a real local Supabase stack
  through a production server. `tools/compare_release.py` accepts the database choice.

## 0.5.0

Optional database feature. Additive: with `database` off (the default), the output of every selection of
`zod`, `forms`, `rest_api` and `cache_components` is byte-identical to 0.4.0 apart from
`.copier-answers.yml` (which gains `database: none`). Projects generated by 0.1.x to 0.4.x upgrade cleanly
and keep their selections. Existing lockfiles are unchanged; four are added.

- New optional feature **`database`**, one validated choice (`none` by default, `postgres`, `supabase`; requires
  `zod`; independent of `forms` and `rest_api`): a local PostgreSQL 17 database (Docker Compose with the image
  pinned by digest, or the pinned Supabase CLI's local stack), version-controlled SQL migrations in
  `supabase/migrations/` shared by both providers with a per-migration checksum lock, a typed server-only
  data-access layer (`pg`, `server-only`; parameterized SQL, pool and timeouts, transactions, safe errors) with
  a Zod-validated sample repository, `npm run db:*` commands, real-database tests (`npm run test:db`) and
  `docs/database.md`. `database` without `zod` is rejected before anything is written. No route uses the
  database: authentication does not exist yet. New locks: `database-postgres+zod`, `database-supabase+zod`
  and each with `forms` (seven in all). With the database off, output is byte-identical to v0.4.0 for every
  selection of `zod`, `forms`, `rest_api` and `cache_components`.
- The Supabase CLI publishes its ports on every network interface; `npm run db:up` checks and fails closed
  (data kept) unless `SUPABASE_ALLOW_LAN_EXPOSURE=true`. Changing an established provider is not an upgrade.
- `tools/features.py` and `features.yml` support choice features. The existing Docker-free tests are
  unchanged apart from generalizing the registry and matrix expectations; the Docker tests run in a separate
  CI job.

## 0.4.0

Optional REST API v1. Additive: with `rest_api` off, the output of every selection of `zod`, `forms` and
`cache_components` is byte-identical to 0.3.0 apart from `.copier-answers.yml` (which gains
`rest_api: false`). Projects generated by 0.1.x to 0.3.x upgrade cleanly and keep their feature
selections. No dependency or lockfile changed.

- New optional feature **`rest_api`** (default off, requires `zod`, independent of `forms`): versioned
  route handlers under `src/app/api/v1/` (`GET /api/v1/app-info`, `POST /api/v1/examples/validate`, and a
  standard 404 for unknown `/api/v1` paths), request and response schemas in `src/lib/schemas/v1/`,
  RFC 9457 problem-details errors with stable machine-readable codes, server-only helpers in
  `src/server/api/`, `docs/api-v1.md`, and tests that call handlers with `Request` objects inside
  `npm run check` (no server, no network). Request bodies are bounded to 8 KiB while streaming, checked
  for media type, UTF-8 and JSON, and parsed with `safeParse`; responses are validated against explicit
  strict schemas; errors never carry stack traces, paths, secrets or submitted values; no CORS headers.
  Within `/api/v1` changes are additive only; a generated contract test pins every field and error code.
  It adds **no npm dependency**: `lock_key` and every `locks/*.json` are unchanged.
- `rest_api=true` without `zod=true` is rejected before anything is written, with raw Copier and
  `copier update`, by an ordinary strict-boolean validator like `forms`' (`rest_api requires zod`);
  `rest_api` never enables Zod. The question is named like the other options, so there is no alias or
  special validation.
- A generated import-graph test keeps `src/server/` away from client components and the shared schemas
  free of framework and environment access.
- Upgrades: enabling the API on an existing Zod project (`copier update --data rest_api=true`) adds its
  files and leaves `package.json`, the lockfile, user files and the Forms selection untouched.

## 0.3.0

Optional Forms feature, plus two maintenance corrections. Additive: with `forms` off, the output is
byte-identical to 0.2.0 apart from `.copier-answers.yml` (which gains `forms: false`) and one added
line in `.prettierignore` (below). Projects generated by 0.1.x and 0.2.x upgrade cleanly and keep their
feature selections. Dependencies changed only for projects that enable `forms`.

- New optional feature **`forms`** (default off, requires `zod`): React Hook Form with the Zod resolver,
  a small accessible example form at `/forms-example` validated by a shared schema in
  `src/lib/schemas/example-form.ts`, and tests that run inside `npm run check` in a DOM environment
  (`jsdom`, per test file). Exact pins: `react-hook-form` 7.91.0, `@hookform/resolvers` 5.9.2;
  development: `@testing-library/react` 16.3.3, `@testing-library/dom` 10.4.2, `jsdom` 30.1.3. The
  example saves and sends nothing. `forms=true` without `zod=true` is rejected before anything is
  written. New lockfile `locks/forms+zod.json` (adds 47 packages, none with install scripts, all
  permissively licensed). With `forms` off, output is unchanged: default and `zod` projects are
  byte-identical to v0.2.0 apart from the documented `.prettierignore` line below.
- `tools/refresh_locks.py` judges "additive" by package identity (name, version, source, integrity)
  instead of by folder, because npm may re-hoist an existing version when packages are added; changed,
  removed or moved direct dependencies still fail.

- Generated projects no longer let Prettier check Copier's `.copier-answers.yml` (root file only, via
  `.prettierignore`). When the template is rendered from an untagged commit, Copier records the
  abbreviated hash as `_commit`; an all-digit hash is serialized single-quoted, which Prettier rejects,
  so `npm run check` failed intermittently. Released tags record `vX.Y.Z` and were not affected. The
  answers file, its serialization and every other source file are unchanged and still checked.
  **Generated-output difference from v0.2.0: exactly one added line**, `/.copier-answers.yml`, in
  `.prettierignore`; every other generated file is byte-identical (verified with
  `tools/compare_release.py v0.2.0 --allow-change .prettierignore`, default and `zod=true`).
- The end-to-end tests record each generated app's gate output and audit before asserting the verdict, so
  a failing gate keeps its evidence, including its exit status. Deterministic tests cover a numeric
  `_commit` (`1234567`) and a deliberately failing gate. `compare_release.py` gained `--allow-change PATH`,
  an exact, visible, single-file allowance that fails if the file did not change.
- CI now uploads downloadable test evidence for every run and Python version, including failed runs:
  JUnit XML, the console record, run metadata tied to the commit under test, installed package
  versions, and for each generated app in the end-to-end tests its gate output and production
  `npm audit` result (`docs/ci-evidence.md`). The exit code is unchanged. The token-shaped-string scan is quiet (matches are never printed) and
  gates both the job summary and the upload. Generated output is not affected.

## 0.2.0

Optional features, starting with Zod. Additive: with every feature off, the output is byte-identical
to 0.1.0 apart from `.copier-answers.yml` (which gains `zod: false`).

- New question `zod` (default `false`): adds the exact-pinned `zod` 4.6.7 dependency, a shared
  schema module in `src/lib/schemas/` (`appInfoSchema`, exported from `index.ts`) with tests for
  accepted and rejected input, and README and `AGENTS.md` guidance.
- Lockfiles are now selected per dependency set from `locks/` (`base.json`, `zod.json`) by a computed
  `lock_key`; no dependency resolution happens at generation. `features.yml` and `tools/` describe
  the supported matrix and regenerate the feature lockfiles from the base lock.
- `package-lock.json` for the default configuration is unchanged.
- Documentation: `docs/features.md`; upgrading notes for feature selections.
- Boolean questions (`zod`, and `cache_components`, which was `type: bool`) are now strict: `type: yaml`
  with `choices: [false, true]` and an `is boolean` validator. Raw Copier used to accept `--data
  zod=banana` as true because it casts a `bool` before validators run; now `banana`, `1`, `y`, an empty
  value and null are rejected before anything is written. Answers are still recorded as booleans, so
  projects generated with 0.1.0 upgrade cleanly (tested).

## 0.1.0 (first release)

Initial release, derived from the reference Web Core baseline.

- Next.js 16, React 19, strict TypeScript, Tailwind CSS v4, shadcn/ui (Radix, Lucide, neutral
  theme, `Button` as the reference component), ESLint, Prettier, Vitest.
- `npm run check` (lint, typecheck, format check, tests, production build) and a GitHub Actions
  workflow that runs `npm ci` and `npm run check`, with commit-pinned actions and read-only
  permissions.
- `AGENTS.md` and `CLAUDE.md` for AI-assisted development.
- Exact dependency versions and a committed lockfile.
- Questions: `app_name`, `app_description` (validated in `copier.yml`) and `cache_components`
  (default on; turns Next.js Cache Components with Partial Prefetching on or off).
- Generation runs no code: no `_tasks`, `_migrations` or Jinja extensions.
- CI on Linux for Python 3.12 and 3.14, including real `npm ci` and `npm run check` runs.
